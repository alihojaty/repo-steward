# Existing policy first

Read tracked policy on the current approved base where possible; distinguish uncommitted proposals. Inspect only relevant manifests, contributor docs, ownership, CI, release tooling, templates and a small sample of recent accepted changes. Determine hosting service, default/integration/maintenance branches, package boundaries, generated assets, lockfiles, LFS and submodules. Do not assume `origin`, `main`, GitHub, SemVer or Conventional Commits. For a new repo record recommendations as proposals, not facts.

## Audit report

For each finding give priority, observed evidence (path, ref or named server rule), consequence, smallest remediation, owner if known and verification. Separate `observed locally`, `verified at host for ref`, `unknown` and `not applicable`. Prioritize loss of work, published credentials, wrong publication target and unprotected critical paths before style. If requested to inspect server rules use approved read access only; no token discovery. Unavailable API ≠ missing rule.

## Bootstrap procedure

1. Inventory what exists, including nested ignore/attributes and repo-specific overrides. Propose minimal independent diffs. Never replace a whole template directory or format the entire repo incidentally. If templates already express a rule, reuse it. No writes for an audit or preview.
2. `.gitignore`: derive candidate paths from the actual toolchain. Prefer narrowly scoped rules for local secrets, caches, coverage and reproducible build products. Keep example env files, source fixtures, migration files, needed workspace metadata and intentional vendored outputs visible. Personal editor preferences belong in a personal exclude file, not necessarily a tracked rule. Ignoring a parent directory prevents re-including a child unless parents are traversable. Test both a positive example (ignored) and a negative example (should remain visible) using `git check-ignore -v --no-index -- <path>`; exit 1 means no match. Examine the actual matching rule, including negations. Check tracked candidates separately with `git ls-files -- <path>`. Never bulk-untrack to make an ignore rule work.
3. `.gitattributes`: inspect existing effective attributes with `git check-attr` on representative source, binary and LFS paths. Agree on text/EOL, platform script exceptions, binary handling and LFS availability before applying. Keep normalization in its own approved PR. A pointer is not evidence that the LFS object is available. Check submodule pointer updates for correct commit and accessibility to consumers.
4. `.editorconfig`, formatter, lockfiles and generated files: resolve conflicting settings with the team. Choose what consumers/builds need to reproduce outputs. If tracking generated output, document the generator/version and a CI drift check. Don't regenerate dependencies or binaries as part of policy setup.
5. `CONTRIBUTING.md`: document the real base branch, branch lifecycle, commit language/style, exact local checks from manifests, PR expectations, release owner and recovery contact. Verify the documented commands exist. Use the host's supported template and ownership locations; validate owner/team names before adding. Document merge strategy and review exception process.
6. CI/host policy: propose required review, owner approval for critical paths, protected branches/tags, required checks, least-privilege job tokens, secret isolation on fork PRs, and an auditable emergency path. Verify a required job reports on every applicable PR (including path-filtered ones); distinguish skipped from success. Hook failures stay visible; hooks are conveniences, not enforcement. For high concurrency consider a merge queue or testing the integrated result. Never weaken policy to unblock a change.
7. Verify actual diff and checks, list unknown host settings and propose a separate admin request if needed. Re-running bootstrap against identical state should propose **no diff**.
